# AI 활용 리포트

근거: `docs/ai-log.md`, 그리고 ai-log 이전 단계(마켓플레이스 제작, 프로젝트 방향 결정)에 대한 작성자 메모.

## 1. 프로젝트 개요
FastAPI로 회원가입, 로그인, JWT 인증 API를 만들었다. 하루 안에 완성하는 학습·포트폴리오용 프로젝트다.

| 항목 | 내용 |
|---|---|
| 기능 | 회원가입, 로그인(액세스·리프레시 토큰 발급), 토큰 재발급, 로그아웃, 내 정보 조회 |
| 기술 | Python 3.14, FastAPI, SQLite + SQLAlchemy(동기), bcrypt, PyJWT, uv |
| 진행 방식 | PRD → ADR → API 스펙 → 구현(PR 3개) → 리뷰 → 머지 |
| 결과 | 엔드포인트 5개, ADR 10개, 테스트 130개 |

처음 기획은 채용공고를 바탕으로 기업 뉴스를 요약하는 서비스였다. 확인해 보니 구글 검색 API는 신규 가입이 중단됐고, 네이버 검색 API는 신규 신청이 중단된 데다 개정 약관상 AI 요약이 금지돼 있었다. 결제 없이 진행하려는 비용 제약도 있어서 범위를 로그인 API로 바꿨다. 프레임워크는 Spring Boot 대신 FastAPI를 골랐다. 1순위 직무(AI 엔지니어)와 연결되고, 직접 만든 python-convention 스킬을 그대로 쓸 수 있기 때문이다.

## 2. AI 작업 환경
AI 도구는 두 가지를 역할을 나눠 썼다.

| 도구 | 용도 |
|---|---|
| Claude 채팅 | 기획 상담, 개념 설명, 결정 추천. ADR과 API 스펙의 결정은 Claude 채팅의 추천과 근거를 내가 검토해 채택했다 |
| Claude Code | 문서 작성, 사실 확인, 구현, 테스트, 리뷰, Git 작업 |

Claude Code에는 직접 만든 마켓플레이스(jaemin-marketplace)를 설치해 썼다.

| 플러그인 | 구성 요소 | 역할 |
|---|---|---|
| jaemin-writer | writing-rules | 모든 문서와 답변의 작성 규칙(필요한 것만, 이모지 금지, 검증된 사실만 단정) |
| | api-spec | API 스펙 문서 형식 |
| | doc-review | 문서 검토. 위치, 문제, 수정안 형식으로 보고 |
| | ai-report | 이 리포트의 구성과 근거 규칙 |
| jaemin-developer | python-convention | 코드 스타일, router/service/repository 레이어, 비밀 정보 관리 |
| | git-workflow | GitHub Flow 브랜치, Conventional Commits(한국어) |
| | code-reviewer (서브에이전트) | PR 전 코드 리뷰. 심각도별 보고 |
| jaemin-log | log-update | 작업이 끝나거나 방법을 바꿀 때 기록 여부를 묻고 `docs/ai-log.md`에 추가 |

스킬은 자동 호출이 보장되지 않는다. 마켓플레이스를 만들 때 AI가 이 한계를 지적했고, 프로젝트 `CLAUDE.md`에 작업 규칙과 개발 순서를 적어 보완했다. 이 밖에 `.claude/settings.json`으로 PR 출처 문구의 이모지를 없앴고, 외부 리뷰로 Codex를 PR에 붙였다.

## 3. 단계별 AI 활용

| 단계 | AI에게 시킨 것 | 사람이 판단한 것 |
|---|---|---|
| 마켓플레이스 제작 | 플러그인·스킬 파일 작성, 커밋 분리(플러그인별 5개 커밋) | 계획의 파일 수를 실제와 대조, 스킬 자동 호출 한계를 CLAUDE.md로 보완하기로 결정 |
| 초기 세팅 | CLAUDE.md, docs 구조 생성. main이 없는 상태와 "main 직접 커밋 금지"가 충돌한다고 지적하고 두 안 제시 | .gitignore만 main에 두고 나머지는 PR로 올리는 안 선택. PR 흐름 연습을 위해 머지는 직접 하기로 함 |
| PRD | 목적, 기능, 비기능 요구사항 작성. 기술 선택은 ADR 결정 항목 9개로 분리 | 무엇을 만들지와 어떻게 만들지를 나눠 결정 근거를 따로 남기기로 함 |
| ADR | 결정 하나당 파일 하나로 9개 작성. passlib, bcrypt 관련 주장을 PyPI, 이슈, 소스, 실행으로 확인 | Claude 채팅의 추천과 근거를 검토해 결정 내용과 이유를 채택함. AI가 채운 선택지는 실제로 비교한 안만 남김 |
| API 스펙 | PRD·ADR에 없는 11개 항목을 추천안과 함께 질문. 스펙과 에러 코드 목록 작성 | Claude 채팅의 추천과 근거를 검토해 결정함(리프레시 토큰은 본문으로 받기, 로그아웃은 멱등하게 처리 등). AI가 제안한 "스펙을 먼저 고친다" 규칙을 검토해 CLAUDE.md에 채택 |
| 구현 PR 1 (기반) | 개발 환경 확인, 의존성 관리 선택지 제시, 설정·공통 에러·DB 구현, code-reviewer 리뷰 | uv + Python 3.14, 동기 SQLAlchemy 선택. 리뷰 반영 범위 결정. 이름이 비슷한 새 패키지(httpx2)는 출처 확인 전까지 보류 |
| 구현 PR 2 (가입·로그인) | 7개 결정 항목 질문, 의존성 출처 확인, 구현과 테스트, 리뷰 반영 | 이메일 소문자화, 없는 이메일도 더미 해시 검증, 리프레시 토큰 SHA-256 저장 등 7개 결정 |
| 구현 PR 3 (재발급·로그아웃·내 정보) | 5개 결정 항목 질문, 트랜잭션 롤백 증명 테스트, 리뷰 반영 | HTTPBearer `auto_error=False` 사용, 교체를 한 트랜잭션으로 처리하고 테스트로 증명하라고 요구 |
| 사람의 검증 | 없음 | 서버를 직접 띄워 Swagger로 가입부터 로그아웃까지 확인. 토큰 교체 후 옛 토큰 재발급은 401, 두 번째 로그아웃은 204로 스펙대로 나옴 |

구현 단계에서 AI는 스펙이나 ADR에 없는 결정을 임의로 정하지 않고, 추천안과 근거를 붙여 물었다. 질문은 스펙 11개, PR 1 4개, PR 2 7개, PR 3 5개로 모두 27개였다. 사람이 정한 결정은 코드보다 스펙이나 ADR에 먼저 반영했다.

리뷰는 doc-review, Codex, code-reviewer 세 겹으로 두었고, 리뷰어마다 다른 문제를 찾았다. 구체적인 사례는 4장에 정리했다.

## 4. AI 오류를 잡은 사례

| 사례 | 무엇이 틀렸나 | 누가 잡았나 | 어떻게 알아챘나 | 어떻게 고쳤나 |
|---|---|---|---|---|
| 계획 숫자 오류 | 마켓플레이스 계획에 파일 14개, SKILL.md 8개라고 함. 실제는 13개, 7개 | 사람 | 계획과 실제 파일을 직접 대조 | 계획 숫자의 오류로 확인하고 실제 구성 기준으로 진행 |
| 다른 레포 맥락 | 다른 레포 창에 보낸 지시를 처리하면서 엉뚱한 레포 기준으로 force push 선택지를 제시함 | 사람 | 제시된 선택지가 현재 레포 상황과 맞지 않음을 확인 | 실행하지 않음 |
| 규칙 미적용 | 초기 세팅을 마치고도 CLAUDE.md 규칙과 달리 기록 여부를 묻지 않음 | 사람 | 규칙대로 묻지 않은 이유를 직접 물음 | 원인은 플러그인 미설치와, 세션 중간에 CLAUDE.md를 만든 것이었음. 플러그인을 설치하고 CLAUDE.md에 묻는 시점을 구체적으로 적음 |
| 검증되지 않은 주장 | Claude 채팅의 추천 이유에 "passlib은 유지보수가 멈췄다"는 확인되지 않은 주장이 들어 있었음 | Claude Code | writing-rules(확실히 검증된 사실만 단정)에 따라 ADR에 쓰기 전에 검증되지 않은 주장임을 짚음 | PyPI와 이슈 트래커로 확인해, 확인된 사실(마지막 릴리스 2020년, bcrypt 4.1 이상 호환 문제)만 출처와 함께 남기고 주장은 제외 |
| 단정 표현 | 마켓플레이스 README에 AI가 직접 쓴 "항상 적용된다" | doc-review | writing-rules 위반 검사 | 단정 표현을 정정 |
| 토큰 중복 | HS256(비밀키 하나로 서명하는 JWT 방식)은 같은 내용이면 같은 토큰을 만들어, 같은 초에 재발급하면 토큰 교체가 무의미해짐. Claude와 사람 모두 설계 단계에서 놓침 | Codex | PR #5 리뷰 | 리프레시 토큰마다 무작위 `jti`(토큰마다 붙이는 고유 ID)를 넣고 DB에 함께 저장(ADR 0005, 0006) |
| 서로게이트 500 | 짝이 없는 서로게이트 문자(UTF-8로 바꿀 수 없는 깨진 유니코드)가 든 비밀번호로 회원가입·로그인 시 500 | code-reviewer | 입력 검토 후 재현 | ADR 0008에 먼저 적고, 회원가입은 `INVALID_PASSWORD`, 로그인은 `INVALID_CREDENTIALS`로 처리. 회귀 테스트 추가 |
| SQLite id 재사용 | 기존 리프레시 토큰을 id로 지워, SQLite가 같은 id를 새 행에 다시 주면 동시 재발급 두 건이 모두 성공함. AI가 처음 쓴 동시성 테스트는 흉내만 내서 놓침 | code-reviewer | 두 스레드로 실제 경합을 만들어 재현 | ADR 0006에 먼저 적고, 재사용되지 않는 `jti`로 삭제. 실제 경합 테스트로 교체 |
| 파일 복원 실수 | 커밋을 회원가입과 로그인으로 나누다가 백업 파일 이름이 겹쳐 파일이 잘못 복원됨 | Claude Code | 복원 직후 파일 내용 확인 | 바로 고치고 테스트 수가 나누기 전과 같은지 확인 |

## 5. 회고

### 잘된 점
- **문서를 먼저 고치고 구현함**: PRD, ADR, 스펙 순서로 썼다. 구현 중 새 결정이 생기면 스펙이나 ADR을 먼저 고쳤다. 그 결과 결정마다 근거 문서가 남았다.
- **리뷰를 여러 겹으로 둔 효과**: doc-review, Codex, code-reviewer가 서로 다른 문제를 찾았다(4장).
- **수정을 테스트로 증명함**
  - 회귀 테스트는 수정 전 코드에서 실패하는 것을 확인했다.
  - 트랜잭션 테스트는 일부러 commit을 둘로 나눈 코드에서 실패하는 것을 확인했다.
  - 그래서 테스트가 통과한다는 사실이 실제 의미를 가진다.

### 아쉬운 점
- **AI가 쓴 동시성 테스트가 흉내만 냄**: 처음 쓴 테스트는 삭제 결과를 0으로 고정하는 방식이라, 실제 경합에서 생기는 버그(SQLite id 재사용)를 놓쳤다. code-reviewer가 두 스레드로 재현하고 나서야 드러났다.
- **초반에 규칙이 적용되지 않음**: 플러그인이 설치되지 않았고, CLAUDE.md는 세션 중간에 만들었다. 그래서 초기 세팅에서는 작성 규칙과 기록 규칙이 빠졌다.
- **Claude와 사람이 모두 놓친 문제**: 토큰 중복은 설계(ADR) 단계에서 걸러졌어야 했다. 하지만 외부 리뷰 전까지 아무도 알아채지 못했다.

### 다음에 바꿀 점
- 동시성이나 트랜잭션처럼 경합이 걸린 로직은 처음부터 실제 경합 테스트를 요구한다.
- 세션을 시작하기 전에 플러그인 설치와 CLAUDE.md 로드를 확인한다.
- 외부 AI 리뷰를 처음부터 리뷰 단계에 넣는다.

### 남은 과제
- 테스트 실행 시 나오는 Starlette의 httpx2 권장 경고는 httpx2 출처를 확인할 때까지 보류했다.

### 소감
실제로 이렇게 해보니 AI가 코딩해도 판단하는 데에 관여를 해야 해서 기술 관련 지식이 많이 필요하다고 생각했다. 지식의 병목이 걸리지 않게.
